# 소싱 신호 8단계 — 데이터 판정 준비 상태

## 목적

7단계의 읽기 전용 소싱 진단 화면은 현재 관측값을 보여주지만, 노출수·실제 테스트 기간·주문 수집 완전성 같은 입력이 없으면 강한/약한 반응을 확정할 수 없다.

8단계는 추천 점수나 행동을 추가하지 않고 **현재 운영 데이터가 어디까지 검증 가능한지**를 별도 readiness 메타데이터로 보여준다.

## 주문 수집 범위

`.env`의 `OARS_ORDER_COVERAGE_START`는 “이 날짜부터 주문 시트가 완전하다고 확인된 시작일”이라는 기존 계약을 그대로 사용한다.

단, 시작일이 존재한다고 바로 최근 비교를 검증하지 않는다. 현재 7/14/30일 비교에서 가장 이른 구간은 이전 30일의 시작일이므로:

- coverage start <= previous 30-day start → 최근 30·14·7일 비교 범위를 모두 포함
- coverage start > previous 30-day start → 일부 구간만 확인
- 미설정 → 미확인
- 잘못된 형식/미래 날짜 → 설정 확인 필요

충분한 coverage가 확인된 경우에만 `snapshot.collectionCompleteness='verified'`를 전달한다.

## 등록일과 판매종료일

MD의 `상품등록일`과 `판매종료일`은 입력 현황과 날짜 형식을 집계한다. 미래 상품등록일은 이상값으로 보류하지만, 미래 판매종료일은 정상적인 예약 종료일로 인정한다.

하지만 다음 추론은 하지 않는다.

- 상품등록일 = 실제 노출 시작일
- 등록 후 경과일 = 실제 테스트 기간
- 판매종료일 입력 = 현재 판매 가능 여부

따라서 등록일/판매종료일 입력률은 참고 메타데이터일 뿐 `exposureKnown`, `testDurationKnown`, `availabilityKnown`을 자동으로 true로 만들지 않는다.

## 상류 데이터 이슈

commerce가 이미 보존하는 `issues`는 ledger/product 범위별 건수만 readiness에 표시한다. 이번 단계에서는 issue 메시지를 이용해 소싱 상태를 새로 승격/강등하지 않는다.

이유는 현재 commerce issue가 판매가, 주문상태, 수량 등 서로 다른 의미를 같은 구조로 담고 있어 소싱 수량에 직접 영향을 주는 오류와 그렇지 않은 오류를 안전하게 구분할 machine-readable code가 아직 없기 때문이다.

## UI

`/sourcing` 상단에 접을 수 있는 **판정 준비 상태** 영역을 추가한다.

표시 항목:

- 주문 수집 범위
- 상품 노출
- 실제 테스트 기간
- 현재 판매 가능 여부
- 상품 등록일 입력 현황
- 판매 종료일 입력 현황
- 상류 데이터 이슈 건수

이 영역은 어디까지나 데이터 검증 상태 설명이며 추천 순위·추천 점수·사입 수량·자동 소싱 행동을 만들지 않는다.

## 상태 활성화

`evidence_strong`과 `weak_observed_signal`은 계속 비활성화한다. readiness가 일부 개선돼도 자동으로 켜지 않는다.

현재 단계에서 확보 가능한 주문 수집 범위만 검증하고, 노출수·실제 테스트 기간·현재 판매 가능 여부가 별도 데이터로 연결되기 전까지 strong/weak 활성화 준비 완료로 간주하지 않는다.
